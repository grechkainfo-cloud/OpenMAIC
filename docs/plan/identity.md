# Фаза 3. Слой идентичности: провайдеры `none`, `test`, `windows`

Статус: **выполнено.** Развилка по §4 решена в пользу подписанной cookie.
Дата: 2026-09-18. Базовый коммит: `e7e7286`.

Запрос: добавить тип авторизации **Test** — вход по имени и паролю,
по умолчанию `admin:admin`. Тип указывается конфигурацией: `Test` или `Windows`.

Это и есть начало фазы 3. Делать Test отдельной заплаткой мимо слоя идентичности
нельзя: через месяц её пришлось бы выпиливать вместе с половиной проводки.
Поэтому план сразу закладывает абстракцию, а Test становится её первой рабочей
реализацией — и заодно тем, на чём фаза 3 отлаживается, пока AD недоступен.

---

## 1. Что уже есть

| Что | Где | Годится ли |
|---|---|---|
| Ворота по общему коду | `middleware.ts`, `/api/access-code/*` | Не идентичность: код один на всех, пользователя не различает |
| HMAC-cookie с проверкой на Edge | `lib/server/access-token*.ts` | **Да**, шаблон переиспользуем целиком |
| Ограничитель попыток | `lib/server/attempt-limiter.ts` | **Да**, отдельный экземпляр под вход |
| Доверие заголовкам прокси | `lib/server/client-identity.ts` | **Да**, за nginx это уже настроено |
| Анонимный владелец данных | `lib/server/agent-runtime/owner.ts` | **Готовый шов.** `resolveRequestOwnerId(req, headers, authenticatedOwnerId?)` — третий аргумент апстрим предусмотрел, но никто не передаёт |

Последняя строка важнее остальных: точка, куда подключается аутентифицированный
субъект, уже есть, и в комментарии к ней прямо написано, что будущая интеграция
обязана её использовать — иначе сессии, созданные под доменной учёткой, окажутся
недоступны её же владельцу.

---

## 2. Конфигурация

```
AUTH_PROVIDER=none | test | windows     # по умолчанию none
AUTH_SESSION_SECRET=<32+ байт случайных>
```

`none` — сегодняшнее поведение без изменений. Это требование: браузерная
персистентность и запуск без авторизации должны продолжать работать.

`AUTH_SESSION_SECRET` обязателен при `test` и `windows`; без него приложение
**не стартует**, а не молча подписывает сессии пустым ключом. Никогда не
`NEXT_PUBLIC_`.

### Провайдер `test`

```
AUTH_TEST_USERNAME=admin                # по умолчанию admin
AUTH_TEST_PASSWORD=admin                # по умолчанию admin
AUTH_TEST_ALLOW_IN_PRODUCTION=          # нужен явный true на стенде
```

Про `admin:admin` нужно сказать прямо: это учётные данные, которые знает
каждый, кто когда-либо видел тестовый стенд. Поэтому:

- пара по умолчанию работает только при `NODE_ENV != production`;
- контурный стенд запускается именно как production, поэтому там потребуется
  осознанный `AUTH_TEST_ALLOW_IN_PRODUCTION=true` — то есть кто-то поставит
  подпись под тем, что вход `admin:admin` на этом стенде допустим;
- при старте с этим флагом в лог уходит предупреждение, один раз, заметное;
- пару можно переопределить через `AUTH_TEST_USERNAME` / `AUTH_TEST_PASSWORD`,
  и на стенде, который увидит кто-то кроме нас, её надо переопределить.

Это не спор с задачей — Test нужен, и он будет. Это способ сделать так, чтобы
он не уехал в эксплуатацию незамеченным.

### Провайдер `windows`

В этой фазе — заглушка, которая честно падает на старте с сообщением
«провайдер windows появится в фазе 5, см. `docs/plan/auth.md`». Место в
конфигурации занимает уже сейчас, чтобы переключение было именно
переключением, а не переписыванием.

## 3. Абстракция

```ts
interface Identity {
  /** Стабильный идентификатор. Для test — `test:admin`; для windows — SID,
   *  а не `DOMAIN\username`: имя меняется при переименовании и переезде
   *  между OU, SID не меняется никогда. */
  subject: string;
  displayName: string;
  roles: Role[];
}

interface IdentityProvider {
  readonly id: 'none' | 'test' | 'windows';
  /** Идентичность текущего запроса, или null — тогда это гость. */
  resolve(req: Request): Promise<Identity | null>;
}
```

Роли на этой фазе: `admin`, `author`, `viewer`. Сопоставление задаётся
конфигурацией — для `test` пользователь получает все три, для `windows`
роли придут из членства в группах AD (`docs/plan/ad-request.md`, п. 9).

---

## 4. Сессия

Вход происходит один раз, дальше работает серверная сессия — то же, что
записано в `auth.md` для SPNEGO.

Cookie `openmaic_session`, подписанная HMAC по `AUTH_SESSION_SECRET`, по образцу
уже существующего `openmaic_access`: `HttpOnly`, `SameSite=Lax`, `Secure` в
production с той же оговоркой `COOKIE_SECURE=0`, что у анонимной cookie, и
временем жизни по `AUTH_SESSION_MAX_AGE_SECONDS` (по умолчанию 8 часов —
рабочий день).

**Развилка, по которой нужно ваше решение.** Подписанная cookie не требует
базы, но её нельзя отозвать до истечения срока. Серверная таблица сессий даёт
отзыв и принудительный выход, но привязывает вход к PostgreSQL.

Предлагаю начать с подписанной cookie: `test` обязан работать без базы (иначе
им нельзя пользоваться в локальной разработке), а отзыв сессии до появления
реальных пользователей нечего отзывать. Таблицу добавить вместе с `windows`,
когда отзыв и обновление групп станут осмысленными. Интерфейс хранилища сессий
заложить сразу, чтобы вторая реализация не ломала вызовы.

## 5. Маршруты и экран входа

| Маршрут | Что делает |
|---|---|
| `GET /auth/login` | Экран входа. Для `test` — форма имени и пароля; для `windows` — редирект на SPNEGO |
| `POST /api/auth/login` | Проверка учётных данных, выдача сессии |
| `POST /api/auth/logout` | Гашение сессии и cookie |
| `GET /api/auth/me` | Текущая идентичность для интерфейса: имя, роли |

Экран входа — на русском, через i18n, с логотипом из `BRAND`, как экран
access-code: бренд показывается до того, как кого-то впустили.

Проверка пароля — сравнение постоянного времени (`timingSafeEqual`), как в
`/api/access-code/verify`. Ограничитель попыток — отдельный экземпляр
`attemptLimiter`, чтобы подбор пароля не сбрасывал счётчик кода доступа и
наоборот.

Что в лог **не** попадает: пароль, значение cookie, содержимое билета. Причина
отказа — попадает, иначе разбирать инциденты нечем.

---

## 6. Проводка

1. `middleware.ts`: при `AUTH_PROVIDER != none` запрос без действительной
   сессии — редирект на `/auth/login` для страниц, `401` для `/api/*`.
   Исключения: сами маршруты входа, `/api/health`, статика бренда.
2. `resolveRequestOwnerId(...)` получает третьим аргументом `subject` из
   сессии. Без этого вошедший пользователь продолжит работать под анонимным
   разделом, и его курсы пропадут при следующем входе.
3. Взаимодействие с `ACCESS_CODE`: при включённом `AUTH_PROVIDER` общий код
   отключается — идентичность старше общего пароля. Если настроены оба, при
   старте пишем предупреждение, что код доступа проигнорирован.

Клиентский `x-learner-key` на этой фазе **не трогаем**: он перестанет влиять
на выбор раздела данных в фазе 4, и делать это раньше — значит менять две вещи
одновременно.

---

## 7. Приёмка

- `AUTH_PROVIDER` не задан → поведение как сегодня, ни один тест не меняется;
- `test` + верные учётные данные → сессия, `/api/auth/me` отдаёт `admin`;
- `test` + неверные → 401, и после N попыток 429;
- пара по умолчанию при `NODE_ENV=production` без опт-ина → приложение не
  стартует, сообщение объясняет почему;
- `windows` → внятный отказ на старте, а не 500 при первом входе;
- выход гасит cookie, следующий запрос снова уводит на `/auth/login`;
- курс, созданный после входа, виден тому же пользователю после logout/login —
  то есть `subject` действительно дошёл до владельца данных.

## 8. Чего этот план НЕ делает

- не разграничивает данные между пользователями — это фаза 4; до неё вход
  ограничивает вход, но не изоляцию;
- не реализует Kerberos — это фаза 5;
- не трогает таблицу авторизации по маршрутам — фаза 4.
