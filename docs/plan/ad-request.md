# Заявка администратору Active Directory

Документ можно отдавать администратору домена **сейчас** — ничего из перечисленного
не зависит от готовности кода. Все пункты одинаковы для обоих вариантов терминации
Kerberos (см. `docs/plan/auth.md`), кроме пункта 3: от выбора зависит только то,
на каком хосте регистрируется SPN.

Обозначения, которые нужно заполнить до подачи:

- `<FQDN>` — полное доменное имя, которое пользователи набирают в браузере,
  например `openmaic.corp.example.ru`
- `<REALM>` — Kerberos-realm, **заглавными**, например `CORP.EXAMPLE.RU`
- `<DOMAIN>` — NetBIOS-имя домена, например `CORP`

---

## 1. DNS-имя сервиса

**Просим:** A-запись `<FQDN>` на IP-адрес обратного прокси (nginx), и обратную
PTR-запись на то же имя.

**Важно: именно A-запись, не CNAME.** Chrome и Edge по умолчанию канонизируют
CNAME перед построением SPN и запрашивают билет на имя цели, а не на то имя,
которое набрал пользователь. Если запись окажется CNAME, вход будет молча
отказывать с видом «билет не пришёл», и найти причину тяжело.

**Проверка:** `nslookup <FQDN>` возвращает запись типа A; `nslookup <IP>`
возвращает `<FQDN>`.

---

## 2. Сервисная учётная запись

**Просим:** отдельную доменную учётную запись, например `svc-openmaic`.

Требования:

- обычная пользовательская учётная запись, **не gMSA** — из gMSA нельзя выгрузить
  keytab;
- «Срок действия пароля не ограничен» либо согласованный регламент ротации
  (см. пункт 4 про KVNO);
- поддержка AES: в `msDS-SupportedEncryptionTypes` должны быть разрешены
  AES128/AES256. RC4 не просим и просим не использовать;
- учётная запись не должна входить в административные группы;
- «Учётная запись важна и не может быть делегирована» — желательно, если это
  не мешает вашим регламентам.

**Проверка:** `Get-ADUser svc-openmaic -Properties msDS-SupportedEncryptionTypes,
PasswordNeverExpires, ServicePrincipalName`

---

## 3. SPN

**Просим:** зарегистрировать `HTTP/<FQDN>` на учётной записи из пункта 2.

```
setspn -S HTTP/<FQDN> <DOMAIN>\svc-openmaic
```

Замечания:

- **FQDN — ровно тот хост, который пользователи набирают в браузере.** Обращение
  по IP-адресу или по короткому имени Negotiate обычно не активирует.
- SPN должен быть **уникален в лесу**. `setspn -Q HTTP/<FQDN>` до регистрации
  обязан не найти ничего: дубликат SPN ломает Kerberos для обеих учётных записей.
- Хост, на котором терминируется Kerberos: при терминации в приложении — сервер
  приложения, при терминации в nginx — сервер nginx. **Если `<FQDN>` в обоих
  случаях один и тот же, разницы нет.** Уточним после вашего решения по
  `docs/plan/auth.md`, но регистрировать можно уже сейчас — SPN привязан к имени,
  а не к машине.

**Проверка:** `setspn -L <DOMAIN>\svc-openmaic` показывает `HTTP/<FQDN>`;
`setspn -X` не сообщает о дубликатах.

## 4. Keytab

**Просим:** сгенерировать keytab для `HTTP/<FQDN>@<REALM>` и передать его
**по защищённому каналу** (не почтой, не в мессенджере, не в тикете).

```
ktpass -princ HTTP/<FQDN>@<REALM> ^
       -mapuser <DOMAIN>\svc-openmaic ^
       -crypto AES256-SHA1 ^
       -ptype KRB5_NT_PRINCIPAL ^
       -pass * ^
       -out openmaic.keytab
```

Что нам нужно знать вместе с файлом:

- **KVNO** (номер версии ключа) на момент выгрузки;
- дату генерации;
- подтверждение, что `-crypto` — AES256, а не RC4.

**Ротация — отдельная просьба зафиксировать в регламенте.** При смене пароля
сервисной учётной записи KVNO увеличивается, и старый keytab перестаёт работать.
Симптом со стороны пользователя — вход просто перестаёт проходить, без внятной
ошибки. Просим:

1. не менять пароль `svc-openmaic` без предупреждения;
2. при плановой смене — заранее согласовать окно и выдать новый keytab;
3. назначить ответственного за эту процедуру.

На нашей стороне: keytab монтируется как секрет, владелец — пользователь
приложения, права `0400`. **В git и в образ контейнера не попадает никогда.**

**Проверка на нашей стороне:** `klist -k -t openmaic.keytab` показывает принципал
и KVNO; `kinit -k -t openmaic.keytab HTTP/<FQDN>@<REALM>` проходит без ошибок.

## 5. Параметры Kerberos для `krb5.conf`

**Просим сообщить:**

- имя realm `<REALM>` и его соответствие DNS-домену;
- FQDN контроллеров домена, которые выступают KDC (минимум два);
- адрес сервера смены пароля (`kpasswd_server`), если отличается;
- нужен ли `dns_lookup_kdc = true` или предпочтителен явный список KDC.

**Проверка:** `kinit <пользователь>@<REALM>` с нашего сервера проходит, `klist`
показывает TGT.

---

## 6. Сетевой доступ (firewall)

**Просим открыть с сервера приложения (и из контейнеров) к контроллерам домена:**

| Порт | Протокол | Назначение |
|---|---|---|
| 88 | TCP и UDP | Kerberos KDC |
| 464 | TCP и UDP | kpasswd (смена пароля) |
| 636 | TCP | **LDAPS** — запрос групп |
| 3269 | TCP | LDAPS к глобальному каталогу (если понадобится междоменный поиск) |
| 53 | TCP и UDP | DNS |
| 123 | UDP | NTP (см. пункт 7) |

Незащищённый LDAP на 389 **не просим** и использовать не будем.

---

## 7. Синхронизация времени

**Просим:** разрешить NTP-синхронизацию сервера приложения (и, отдельно,
хост-системы контейнеров) с контроллерами домена, и подтвердить, какие серверы
считать источником.

Kerberos по умолчанию не прощает расхождения больше пяти минут. Это самая частая
причина отказа с формулировкой «внезапно перестало работать».

**Проверка:** расхождение времени сервера приложения и контроллера домена менее
30 секунд; в контейнерах время наследуется от хоста (в них отдельного NTP-клиента
не будет, поэтому важна синхронизация именно хоста).

## 8. Учётная запись для LDAP-запросов групп

Членство в группах мы читаем отдельным LDAPS-запросом после успешной
аутентификации — декодировать PAC из билета трудоёмко и хрупко.

**Просим:**

- отдельную учётную запись **только на чтение**, например `svc-openmaic-ldap`
  (можно ту же, что в пункте 2, но лучше отдельную — у неё другой режим ротации);
- Base DN для поиска пользователей и групп;
- подтверждение, что доступны атрибуты: `objectSid`, `sAMAccountName`,
  `displayName`, `mail`, `memberOf`;
- **корневой сертификат внутреннего УЦ** в формате PEM — для проверки LDAPS;
- ответ, нужны ли **вложенные группы**. Если да, просим подтвердить, что
  допустим поиск через `LDAP_MATCHING_RULE_IN_CHAIN`
  (`memberOf:1.2.840.113556.1.4.1941:`) или что доступен `tokenGroups`.

Почему `objectSid`: идентификатор пользователя в наших данных должен быть
неизменяемым. `<DOMAIN>\username` меняется при смене фамилии, SID — нет.
На SID будут завязаны все данные пользователя, поэтому это не косметика.

**Проверка:** `ldapsearch -H ldaps://<dc-fqdn> -D "<bind-dn>" -W -b "<base-dn>"
"(sAMAccountName=<тест>)" objectSid displayName memberOf` возвращает результат.

## 9. Группы AD для ролей приложения

**Просим создать (или назвать существующие) три группы** и сообщить их
полные DN:

| Роль в приложении | Что даёт | Группа AD |
|---|---|---|
| `learner` | проходит курсы | `<заполнить>` |
| `author` | создаёт и редактирует курсы | `<заполнить>` |
| `admin` | администрирование, права, аудит | `<заполнить>` |

Сопоставление «группа → роль» задаётся конфигурацией приложения, не кодом, —
переименование группы правится без пересборки.

Отдельно просим ответить: **что делать с пользователем, аутентификация которого
прошла, но ни одна группа не даёт роли.** Варианты: отказ с понятным сообщением
(предпочтительно), либо неявная роль `learner` для всех сотрудников домена.

## 10. Групповая политика: зона «Местная интрасеть»

Браузер не отправит Kerberos-билет сам по себе. Хост должен попадать в зону
«Местная интрасеть».

**Просим раздать групповой политикой:**

- **Chrome и Edge:** политика `AuthServerAllowlist` (ранее `AuthNegotiateDelegateWhitelist`
  относится к делегированию — его не просим) со значением `<FQDN>`.
  Альтернатива — добавить `<FQDN>` в «Местная интрасеть» через настройки
  Internet Explorer, которые Chrome и Edge на Windows читают.
- **Firefox**, если он используется: `network.negotiate-auth.trusted-uris` = `<FQDN>`
  через политику Firefox (`policies.json` / ADMX).

**Проверка:** на рабочей станции в `chrome://policy` видна `AuthServerAllowlist`
с нашим FQDN; в `about:config` Firefox — соответствующее значение.

---

## 11. Сертификат TLS

**Просим:** сертификат для `<FQDN>` от внутреннего УЦ, с приватным ключом,
переданный защищённым каналом; плюс цепочку УЦ.

Сессионная cookie будет `Secure`, поэтому HTTP-доступ не предусматривается вовсе.

**Проверка:** сертификат содержит `<FQDN>` в SAN (не только в CN); цепочка
проверяется на типовой рабочей станции без предупреждений.

## 12. Организационные вопросы (нужен ответ, не настройка)

1. **Нужен ли доступ с недоменных машин?** Если да — предусматриваем форму входа
   с проверкой логина и пароля через LDAP bind. Требуется ваше подтверждение,
   что такой сценарий допустим политикой безопасности.
2. **Политика блокировки учётных записей.** Сколько неудачных попыток до
   блокировки и на какой срок — нам нужно ограничить частоту попыток на своей
   стороне так, чтобы подбор через нашу форму не блокировал доменную учётную
   запись сотрудника.
3. **Ответственный за keytab и его ротацию** — имя и способ связи.
4. **Тестовая учётная запись** в домене для приёмки, с членством во всех трёх
   группах ролей поочерёдно.
5. **Есть ли NGINX Plus** либо согласованная эксплуатацией сборка nginx
   с модулем SPNEGO. Это влияет на архитектурное решение, см. `docs/plan/auth.md`.
