# Смена бренда

Инструкция по ребрендингу. Полный цикл — правка одного файла, замена файлов в
одной директории, одна команда генерации и четыре проверки.

Исходный план и инвентаризация — `docs/plan/branding.md`.

---

## Коротко

```bash
# 1. значения бренда
$EDITOR lib/brand/brand-config.ts

# 2. файлы (см. §2)
#    public/brand/*, app/favicon.ico, app/apple-icon.png

# 3. пересобрать CSS-токены из конфига
pnpm run gen:brand-tokens

# 4. проверить
pnpm run check:brand-contrast
pnpm run check:brand-fonts
pnpm test
pnpm test:e2e -- brand-appearance --update-snapshots
```

Правки в `components/` и `app/` не нужны — и запрещены правилом ESLint
(см. §6).

## 1. Значения: `lib/brand/brand-config.ts`

Единственный файл со значениями. Всё, что ниже комментария
`ЗАПОЛНИТЬ ПРИ РЕБРЕНДИНГЕ`, принадлежит бренду.

### Идентичность

| Поле | Что это | Где видно |
|---|---|---|
| `productName` | полное название | заголовок вкладки, `alt` логотипа, метаданные, переводы через `{{brand}}` |
| `shortName` | короткое название | узкие места; `{{brandShort}}` |
| `agentName` | как продукт называет свой агент-автор | `{{brandAgent}}` в переводах |
| `slogan` | **необязательное** | если задано — вытесняет переведённый `home.slogan`. См. §5 |
| `metaDescription` | `<meta name="description">` | не переводится, см. §5 |
| `legalFooter` | строка правообладателя внизу главной | пустая строка убирает футер целиком |
| `supportContact` | контакт техподдержки | |
| `userAgent` | `User-Agent` исходящих запросов продукта | SearXNG и прочие внешние вызовы |

### Логотипы

| Поле | Что это |
|---|---|
| `logo.light` | горизонтальный логотип для светлого фона, путь от корня `public/` |
| `logo.dark` | то же для тёмного фона. **Необязательное**: если не задано, в тёмной теме используется светлый вариант |
| `logo.mark` | квадратный знак (шапка воркспейса, PBL) |
| `logo.hasWordmark` | несёт ли горизонтальный логотип само название. `false` — рядом с квадратным знаком будет дорисовано `productName` цветом `themeColor` |

Тест `tests/lib/brand/brand-config.test.ts` падает, если объявленный файл
отсутствует: конфиг, указывающий на несуществующий логотип, ломает главную,
класс и экран входа сразу, и делает это молча — битой картинкой, а не ошибкой.

### Цвет и типографика

| Поле | Что это |
|---|---|
| `themeColor` | `<meta name="theme-color">` и цвет вордмарка в Pro-воркспейсе |
| `theme.radius` | `--radius`; остальная шкала скруглений выводится из него |
| `theme.light`, `theme.dark` | **31 токен на тему.** Каждый становится CSS-переменной: `primaryForeground` → `--primary-foreground`, `chart1` → `--chart-1` |
| `fonts.ui` | `--font-sans` |
| `fonts.slideDefault` | шрифт рендерера слайдов по умолчанию |
| `fonts.pptxExport` | шрифт, вписываемый в `.pptx`. См. §4 |
| `fonts.slidePromptFamily` | семейство, которое называем модели при генерации разметки |

## 2. Файлы

### Заменить содержимое, пути не трогать

```
public/brand/logo-horizontal.png   ← logo.light
public/brand/mark.png              ← logo.mark
```

Пути — это значения `logo.*` в конфиге; можно назвать файлы иначе, тогда
поправьте конфиг. Формат любой, который понимает браузер (PNG, SVG, WebP).

Тёмный вариант логотипа: положите файл и добавьте `logo.dark`. Если его нет —
не добавляйте поле: светлый логотип будет использован в обеих темах. Это
честнее, чем дублировать светлый файл под именем тёмного.

### Заменить обязательно — эти два имени резолвит Next.js

```
app/favicon.ico
app/apple-icon.png
```

Next.js находит их **по имени файла**. Через конфиг их указать нельзя — это не
недоработка, а то, как устроены file-conventions в App Router. Поэтому
в `brandMetadata()` намеренно нет поля `icons`: объявить их ещё и там значило бы
получить второй `<link rel="icon">`.

### Не трогать

- `public/logos/` — логотипы **сторонних** провайдеров (OpenAI, Qwen, FunASR…).
  Это не наш бренд.
- `public/avatars/` — аватары агентов, нейтральные.
- `LICENSE` и авторские уведомления в исходниках. Проект под MIT, их сохранение —
  условие лицензии, и ребрендинг его не отменяет.

## 3. Генерация CSS-токенов

```bash
pnpm run gen:brand-tokens
```

Перезаписывает `app/brand-tokens.css` из `BRAND.theme`. Файл сгенерированный,
руками его править нельзя — `app/globals.css` его импортирует, и никаких
`:root` / `.dark` блоков в `globals.css` больше нет.

Забыть эту команду безопасно: `tests/lib/brand/brand-tokens.test.ts` падает,
если файл разошёлся с конфигом. То есть расхождение ловится `pnpm test`,
а не кривым цветом в проде.

## 4. Проверки

### Контраст

```bash
pnpm run check:brand-contrast
```

Считает WCAG-контраст для **обеих** тем (палитра, которая хорошо читается
в светлой теме и нечитаема в тёмной, — это нормальный способ сломаться).

Две категории:

- **required** — текст на поверхности (4.5:1) и индикатор фокуса (3:1,
  SC 2.4.11). Провал → ненулевой код возврата;
- **advisory** — декоративные границы и серии графиков. Число печатается,
  сборку не роняет. Обоснование — в шапке скрипта.

Понимает `#hex` и `oklch()`. Цвет, который он не смог разобрать, **считается
провалом**, а не «ок»: молчаливо неверная проверка хуже отсутствующей.
Математика вынесена в `lib/brand/contrast.ts` и проверена по эталонным
значениям WCAG в `tests/lib/brand/contrast.test.ts`.

### Кириллица в шрифтах

```bash
pnpm run check:brand-fonts
```

Открывает каждый woff2 через `fontkit` и спрашивает реальные глифы — по
семейству **и по начертанию**. Имена файлов не анализируются.

Зачем: шрифт с кириллицей в Regular и без неё в Bold не падает. Браузер
подставит системную гарнитуру для недостающего веса, и страница поедет двумя
шрифтами, часто посреди предложения. Всплывает это как «жирный текст выглядит
странно» — через недели после ребрендинга.

Набор проверяемых шрифтов выводится из импортов `app/layout.tsx` и
`app/editor-fonts.ts`, так что новый шрифт попадает под проверку сам.

Список исключений (`SCRIPT_SPECIFIC_PACKAGES`) — китайские акцидентные
гарнитуры из пикера редактора: требовать от них кириллицу неправильно.

### Тесты и линт

```bash
pnpm test          # в т.ч. drift-тест токенов и запрет бренда в переводах
pnpm lint          # запрет литералов бренда и цветов, см. §6
```

### Скриншоты

```bash
pnpm test:e2e -- brand-appearance --update-snapshots
```

`e2e/tests/brand-appearance.spec.ts` — единственные тесты в наборе, которые
проверяют пиксели: главная в обеих темах, экран ввода кода доступа, класс.
Все остальные спеки продолжат проходить, даже если логотип исчезнет, токены
темы перестанут резолвиться или кириллица уедет в системный шрифт.

### PPTX — проверяется только руками

`pptxgenjs` **не встраивает шрифты** в файл. `fonts.pptxExport` обязан быть
семейством, которое есть на машинах, где файл откроют.

Сейчас это `Segoe UI`: есть на любой Windows начиная с Vista, полная кириллица.
Корпоративный шрифт допустим, только если он раскатан групповой политикой на
все рабочие места.

Проверка — открыть реальный `.pptx` в PowerPoint на типовой рабочей станции.
Из кода это не проверяется никак.

## 5. Почему слоган и описание живут по разным правилам

- **`home.slogan`** — проза, значит переводится и лежит в
  `lib/i18n/locales/*.json`. Поле `BRAND.slogan` — необязательное
  *переопределение* для бренда, чей слоган это фиксированная фраза,
  не подлежащая переводу. Читать нужно через `useBrandTagline()`, а не через
  `t('home.slogan')`, иначе переопределение сработает не везде.
- **`metaDescription`** переводиться не может: Next.js резолвит метаданные на
  сервере, до того как известна клиентская локаль. Одна строка на развёртывание,
  пишите на основном языке контура.

**Название бренда в переводах не хранится вообще.** В JSON стоит `{{brand}}`,
`{{brandShort}}`, `{{brandAgent}}`; значения подставляются автоматически —
через `interpolation.defaultVariables` в `lib/i18n/config.ts` и через те же
умолчания в hook-free `createWorkbenchTranslator`. Оба транслятора обязаны
резолвить одинаково, поэтому умолчания у них общие
(`BRAND_INTERPOLATION_DEFAULTS`). Тест `tests/lib/brand/brand-i18n.test.ts`
падает, если название снова окажется вписанным в перевод.

## 6. Что защищает инвариант

Правило `no-restricted-syntax` в `eslint.config.mjs`:

- **литералы названия** (`OpenMAIC`, `MAIC Agent`) запрещены в `app/**`
  и `components/**` — в строках, в JSX-тексте и в шаблонных литералах.
  Единственное исключение — `components/chat/element-reference-receipt.ts`:
  там имя заголовка протокола `X-OpenMAIC-Element-Reference-Accepted`,
  согласованное с `lib/chat/pi/element-reference.ts` и e2e. Переименовать
  его вместе с брендом значило бы сломать контракт, а не соблюсти его;
- **hex-литералы цвета** запрещены в `app/**` (кроме `app/eval/**` —
  это стенд разработчика, цвета там фикстуры).

Оба блока ESLint идут последними и поэтому *заменяют* репозиторный
`no-restricted-syntax`; именно поэтому каждый из них заново подмешивает
`AI_SDK_DYNAMIC_IMPORT_BAN`. Если будете их трогать — не потеряйте это.

## 7. Известный долг — конфигом пока не покрыто

Честный список того, что ребрендинг всё ещё не достаёт.

### Цветовые литералы в `components/`

```bash
grep -rnoE "'#[0-9a-fA-F]{3,8}'|\"#[0-9a-fA-F]{3,8}\"" --include=*.ts --include=*.tsx components | wc -l
```

Около 90 штук в ~29 файлах: внутренности рендерера слайдов, собственная
тёмная хромота PBL-поверхности, дефолты графиков. Это настоящий долг, но
выплачивается он дизайн-проходом, а не флагом линтера, поэтому правило на них
намеренно не распространено.

### Палитра в промптах генерации

Системные промпты генерации содержат зашитые цвета:
`packages/@openmaic/generation/templates/slide-content/system.md` — 25 hex,
`visualization3d-content/system.md` — 17,
`procedural-skill-content/system.md` — 13, плюс
`lib/prompts/snippets/whiteboard-reference.md`.

Модель раскрашивает слайды и интерактивные сцены этой палитрой независимо от
темы приложения. Подстановка палитры из конфига запланирована **после фазы 2.5**,
чтобы переписать промпты один раз — язык и палитру вместе, а не два раза.

### `configs/theme.ts`

`PRESET_THEMES` (16 офисных тем) **не используется ни одним потребителем** —
проверено поиском по репозиторию. Это заготовка под пикер тем, который не
подключён. Добавлять туда корпоративную тему сейчас значило бы плодить мёртвый
конфиг; вернёмся, когда пикер появится.

### Шрифты рендерера — решено

`packages/@openmaic/renderer/fonts.css` объявлял шесть `@font-face` на внешний
origin. Список вычищен: `FONT_FAMILIES` пуст, генератор **отказывается**
собирать CSS с `src` на стороннем origin. Подробности — в
`packages/@openmaic/renderer/fonts.config.mjs`.

### Пикер шрифтов — решено

`configs/font.ts` объявляет письменности каждой гарнитуры, `fontsForScript`
фильтрует список по языку интерфейса, а `tests/configs/font-scripts.test.ts`
сверяет объявления с самими файлами шрифтов. Заодно нашлось, что запись
`Inter` указывала на семейство, которого нет: загружается `Inter Variable`,
поэтому выбор «Inter» молча откатывался на системный шрифт.

### Прочее

- `docker-compose.yml`: сервис `openmaic`, тома `openmaic-data` /
  `openmaic-postgres`, `POSTGRES_DB/USER=openmaic`. Переименование на живом
  стенде равно потере данных — нужна процедура миграции;
- `package.json` → `"name": "openmaic"`, npm-скоуп `@openmaic/*`;
- артефакты апстрима удалены: `packages/docs` (сайт документации), `skills/openmaic`,
  `assets/*.gif` (демо, ~83 МБ), `community/`, `README-zh.md`, `CONTRIBUTING.md`,
  `SECURITY.md`, шаблоны issue и PR, триаж, workflow публикации в npm и ClawHub.
  В `.github/workflows` остались `ci.yml` (без задачи `issue-triage`) и
  `storage-pg-contract.yml` — форку нужен свой прогон тестов;
- внутренние идентификаторы, которые намеренно оставлены как есть:
  `compositionId: 'openmaic'` и `openmaic-video-manifest.json` в видеоэкспорте,
  заголовок `X-OpenMAIC-Element-Reference-Accepted`, ключ localStorage
  `maic:account:settings-storage`. Это контракты, а не витрина.

| `scripts/generate-brand-tokens.ts` | генератор |

| `scripts/check-brand-fonts.ts` | проверка кириллицы |
